# The Stack Beneath Family Intelligence — v2

**Date:** 2026-07-22
**Status:** Architecture reference
**Re:** Breaking the family appliance out into a generic private-intelligence
platform — ordered from the application runtime down through the device, with
the inter-device fabric at the very bottom.

---

## Premise

[intelligence.family](https://www.intelligence.family/) describes a vertical product: local language models that preserve family memory, embodied in three devices (the Leaf, the Radio, the Family Book), running an on-device ETL pipeline — capture and chunk audio, diarise and transcribe with offline models (pyannote-audio, faster-whisper), compress with Chain-of-Density prompting, and load the result into an ontological graph of People, Events, and Locations. It commits to encryption at rest, a physical disconnect switch, and the promise of "verifiable proof that our data's accessible to us alone."

Treat all of that as the **reference application**. The family use case is one tenant of a horizontal platform: a private, multi-device, agentic appliance stack that any vertical could sit on — a household archive today; a clinic, a workshop, a small firm's institutional memory tomorrow. This document breaks that platform into its discrete parts.

**Ordering note for v2.** Layers 1–9 describe a *single device*, top to bottom: from the application runtime down to silicon. Layers 10–11 sit beneath even that — they are the **inter-device fabric** that welds a fleet of such devices into one system. Replication and transport aren't features of a device; they're the substrate the devices stand on.

**Inference note for v2.** There is no external model plane. Models run on the device, period. Every model invocation in this stack — interactive or pipeline — resolves to local silicon. This deletes the only policy-governed trust boundary from v1: nothing in this system leaves a device unencrypted, ever, and the entire trust story becomes cryptographic.

---

## Two off-device planes

Two services exist outside the devices. Both attach at specific layers, and neither can read content:

**The data plane — the sync server for the Opaque Mirror.** A store-and-forward mirror that holds only ciphertext and never holds keys, modeled directly on how Signal treats its servers (detailed at Layer 11). It exists so devices that are never online at the same moment can still converge, and so the family has off-site durability. Attaches at Layer 11.

**The control plane — the fleet service.** Signs firmware, stages rollouts, distributes model weights, and reads device *health* — never content. It can brick a device but cannot read one. Attaches at Layer 6.

## Layer 1 — Application runtime

**What the family products are instances of.** The Leaf, the Radio, and the Family Book are not three products; they are three clients of one runtime with different interaction surfaces — ambient voice capture, tactile browsing, read/write scrapbook. The runtime is what makes the family use case generic: an app SDK, a set of UI surfaces (voice, tactile controls, screen), an app lifecycle, and a permission model.

The one architectural rule that matters here: **apps never touch raw keys or raw sensor streams.** They see governed views — queries against the knowledge layer, subscriptions to its change feed, and capability-scoped access to device functions. The site's design tenets (Timeless, Observable, Trustworthy) are enforced *below* the app, so a third-party vertical can't quietly violate them.

Responsibilities: app packaging and lifecycle; query/subscription API onto Layer 4; capability grants ("this app may read the Person graph but not raw audio"); rendering across the device family.

---

## Layer 2 — Agentic harness: Pii

The onboard orchestration layer is **Pii** — a custom harness in the spirit of [GSD (Get Shit Done)](https://gsd-build-get-shit-done.mintlify.app/introduction): spec-driven, deterministic workflow scaffolding wrapped around a model, rather than a free-running agent loop. Work is decomposed into atomic, contract-bounded tasks, each executed with fresh context, with the plan — not the model's memory — carrying state between steps.

On an appliance this is not a style preference, it's a physical necessity. Local models on Orin-class silicon have small context windows and no tolerance for context rot; a GSD-style architecture is what makes small models *reliable* — the harness supplies the rigor, the model supplies the language. The site's ETL pipeline is exactly this shape already: a fixed spec (extract → transform → load, with "forensic accuracy" extraction contracts) executed step by step by whatever model is on board.

**Model-agnostic now means agnostic across local backends.** One adapter contract; behind it, llama.cpp / ONNX Runtime / TensorRT-class runtimes, whisper- and pyannote-class specialist models, and whatever ships next. Weights are swappable fleet artifacts (delivered through Layer 6), so the harness must never encode assumptions about a specific model's quirks — the spec layer is the stable interface, models are replaceable parts underneath it.

**Job scheduling.** Two workload classes with different latency contracts: interactive turns (someone talking to the Radio) and long-running background pipelines (overnight ETL over the day's audio). Pii schedules both against the resource governor in Layer 7.

What v1 called the "escalation policy engine" is gone, and its deletion is a feature: with no remote model plane, there is no cleartext egress to govern. The most dangerous component in the v1 architecture no longer needs to exist.

## Layer 3 — Ingestion pipelines & the encrypted data sink

The site's ETL pipeline, generalized into a **pipeline runtime** with application-defined stages.

**The encrypted data sink** is the capture path: sensor data (audio, for the family application) is written straight to storage through an encrypt-on-write, append-only, crash-safe landing zone. Plaintext never touches disk — this is the mechanism behind the site's "records directly to storage with encryption at rest." The sink is deliberately dumb: it accepts sealed chunks and durability-acknowledges them, nothing more, so the capture path stays simple enough to audit and fast enough to never drop audio.

**Transform stages** run as Pii background jobs: diarisation and voiceprint extraction, transcription, Chain-of-Density compression, entity and relation extraction. Each stage is a pluggable unit with a declared input/output contract, so a different vertical swaps the stage list without touching the runtime. The family pipeline (pyannote → whisper → CoD → graph extraction) is just the reference configuration.

**Load** emits structured writes into Layer 4 — and every write carries provenance back to the sealed source chunk, so any extracted "fact" can be traced to the audio that produced it.

## Layer 4 — Knowledge & blob storage

The ontological database, generalized. Three stores behind one storage service:

**The graph.** Property graph with an application-defined schema — Person / Event / Location with RELATES_TO / HAPPENED_AT / ATTENDED edges for the family app. The site prototypes on Neo4j; an embedded engine (Kùzu-class) is the likelier shipping choice on appliance hardware.

**The blob store.** Raw and derived media, content-addressed. Content addressing buys deduplication for free and — more importantly — makes blobs immutable, which Layer 10 will exploit: immutable objects never conflict.

**Indexes.** Vector indexes for retrieval, full-text for transcripts.

The storage service is the *only* path to disk for Layers 1–3. It enforces encryption at rest using keys it borrows from Layer 5, and it emits a totally-ordered local change log — the raw material Layer 10 replicates.

## Layer 5 — Cryptographic core & key management

Both encryption commitments — at rest and end-to-end — resolve to this one layer. It owns the key hierarchy:

**Hardware-rooted device identity** (sealed in Layer 8) → **device storage keys** (encryption at rest, serving Layers 3–4) → **the family keyset** (group E2EE across the household's devices — an MLS-style or Signal-sender-keys-style group, where membership *is* the set of enrolled devices) → **per-object content keys** (so individual objects can be shared, expired, or shredded independently).

Three ceremonies define the user experience of this layer, and they must match the site's Observable/Trustworthy tenets:

**Enrollment.** Adding a device to the family is a physical, legible act — QR exchange or physical touch between devices — after which the newcomer holds the family keyset and can restore the full replica through Layer 11's Mirror.

**Revocation.** A lost or stolen Leaf triggers key rotation: the family keyset rolls forward, the Mirror's future ciphertext is opaque to the lost device, and its hardware identity is expelled from the fleet.

**Recovery.** A zero-knowledge Mirror means the vendor *cannot* reset lost keys — that's the point, and it must be a deliberate, loudly-communicated stance. Recovery is social (quorum of surviving family devices), physical (a printed recovery code in the family book, fittingly), or — the middle path Signal found — enclave-enforced: see the Secure Value Recovery note at Layer 11. Never vendor escrow.

## Layer 6 — Fleet management & FOTA ⟵ *control plane attaches here*

The vendor-facing plane, kept structurally incapable of touching content.

**FOTA.** Signed A/B image updates with automatic rollback (RAUC / Mender / SWUpdate-class machinery), staged rollouts across the fleet, and an update cadence commitment measured in decades — the site's "Timeless" tenet is a *firmware contract*, not just an industrial-design one.

**Model weight distribution.** With no external model plane, this channel carries the entire intelligence of the product: weights are large, versioned artifacts, swappable independently of the OS image (Pii's model-agnostic adapter in Layer 2 is what makes this safe). Delta updates matter at these sizes, and distribution between a household's own devices can piggyback on Layer 11's gossip — the vendor ships weights to one device, the home's mesh spreads them.

**Attestation-gated enrollment and health.** The fleet plane consumes Layer 8's attestation quotes: a device joins the fleet (and the family, via Layer 5) only after proving what code it booted. Telemetry is privacy-preserving by construction — boot status, storage health, update state, thermals; aggregated or differentially private where it leaves the device; and *never* anything derived from content.

---

## Layer 7 — OS & platform services

An embedded Linux (Yocto or Nix-image class) whose defining features are:

**A verified chain.** Measured boot from Layer 8's root, dm-verity-protected system partitions, and a read-only OS image that FOTA replaces atomically.

**Sandboxed services.** Every layer above runs as an isolated service (systemd hardening, seccomp, or microVM isolation for the riskiest parsers — media decoders chew on untrusted input all day).

**The disconnect switch as a driver-level truth.** The physical switch cuts microphone power in hardware. The platform's job is to make that state *observable* to software (so the Leaf's UI can reflect it, so Pii pauses pipelines) while remaining *non-overridable* by software. Privacy the user can feel with a thumb, per the site.

**The resource governor.** One NPU/GPU, two masters: interactive agent turns and background ETL. The governor arbitrates — the site's own benchmarks (a 3:42 story processed on Thor, Orin, and a Pi 5) are effectively the sizing study for this component, and with local-only inference the stakes rise: there is no cloud overflow valve, so scheduling policy *is* the product's responsiveness.

---

## Layer 8 — TEE & hardware root of trust

The trusted execution environment, authenticated by hardware: immutable boot ROM → secure boot → measured boot → **remote attestation**. Concretely: OP-TEE on Arm TrustZone for Orin/Pi-class parts, with per-SoC equivalents as the hardware menu evolves.

What runs inside the TEE, and nothing else:

**Key custody.** Layer 5's root keys are generated inside and never exist outside. Crypto operations happen in the TEE; the rich OS sees only ciphertext and handles.

**Attestation.** Quotes for Layer 6 (fleet enrollment) and — more interestingly — for *peers and owners*: a device can prove to the family's other devices, and to the family itself, exactly what code it is running. This is the technical substance behind the site's central promise, "safe in the verifiable proof that our data's accessible to us alone." Verifiable is a cryptographic claim, and this layer is where it's made.

**Sensitive inference (selectively).** Voiceprints are biometrics. Sealing diarisation embeddings and the speaker-matching step to the TEE means even a compromised rich OS can't exfiltrate the family's voice identities.

Note the symmetry with Layer 11: here, devices attest *to the fleet and to each other*. In Signal's architecture the direction inverts — clients use remote attestation to verify code running on the *server* (contact discovery, Secure Value Recovery). The Opaque Mirror can borrow that trick where it helps.

---

## Layer 9 — Hardware

The physical floor of the single-device stack:

**Compute.** The site's benchmark ladder — NVIDIA Thor, NVIDIA Orin, Raspberry Pi 5 16GB — is the current menu, with the stated bet that small chips with integrated AI acceleration are coming. Local-only inference makes this the load-bearing bet of the whole product: the NPU is not an accelerator, it is the sole home of the intelligence. The platform decision is to treat the SoC as swappable (which Layers 6 and 7 must support) rather than betting the product on one part.

**Security silicon.** A secure element or TPM — discrete or on-die — anchoring Layer 8.

**Capture and control.** The mic array, the tactile surfaces, and the physical disconnect switch as a first-class BOM item with its own certification story, not an afterthought.

**Storage.** Sized for years of family media, with an archival-format commitment: the "Timeless" tenet means bytes written today must be readable by a device that doesn't exist yet.

**Industrial design.** Generational durability back-pressures the whole stack: hardware that must outlive multiple software generations forces the long-horizon FOTA commitment in Layer 6 and the stable storage formats in Layer 4.

## Layer 10 — Replication & conflict resolution

Multi-device is not an edge case; it is the product (three devices in one home, day one). The change log from Layer 4 becomes a replicated log, and conflict resolution happens in two tiers:

**The deterministic tier: CRDTs.** Graph mutations map naturally onto well-understood CRDTs — observed-remove / add-wins sets for edge membership, last-writer-wins or multi-value registers for scalar properties, with per-ontology-type merge policy declared in the application schema. Blobs are content-addressed and immutable, so media never conflicts. This tier guarantees convergence without coordination: any subset of devices that can talk will agree.

**The semantic tier: entity resolution.** The genuinely hard conflicts are not concurrent writes — they're concurrent *meanings*. Two devices independently extract "Aunt May" from different conversations: same node or two people? That is a merge-time entity-resolution problem, and it's agent-assisted — Pii proposes merges, the deterministic tier records them as first-class, *revertible* merge operations (never destructive rewrites), and ambiguous cases surface to a human through the app layer. Deterministic convergence below, semantic reconciliation above.

## Layer 11 — Transport: gossip + the Opaque Mirror ⟵ *sync server attaches here*

One replication protocol, two transports — and the E2EE boundary.

**End-to-end encryption lives at this seam.** Anything serialized for *any* transport is sealed to the recipient device keys (from Layer 5) before it leaves the process. The transports below this line are untrusted by construction, which is what makes the rest of the layer simple.

**Transport one: peer-to-peer gossip.** For devices that can reach each other but not the internet — same LAN, or the case called out in the brief: devices on a shared VPN mesh where the VPN is up but the network behind it is not. Discovery via mDNS on the LAN and lightweight rendezvous over the mesh; then anti-entropy gossip — peers exchange version vectors, compute the delta, and epidemically disseminate missing log entries and blobs. Any two devices that can exchange packets will converge with no server involved. Gossip is the *preferred* transport; the Mirror is the fallback for devices that never overlap in time.

**Transport two: the Opaque Mirror — Signal's server model, applied to storage.**

Signal is the strongest production reference for what "zero-knowledge" should mean here, because Signal's answer is architectural, not contractual — the server *cannot* betray what it never learns. Four of its mechanisms transfer directly:

**1. The server as an untrusted ciphertext router.** Signal's servers queue and forward sealed envelopes and store almost nothing — famously, Signal's only possible responses to subpoenas have been an account's creation date and last-connection date, because that is the entire retained record. The Mirror adopts the same posture as a *storage* server: it holds sealed log entries and padded blobs against opaque handles. Its complete knowledge of a family is: some ciphertext exists, of certain (padded) sizes, touched at certain times. That list should be published as the Mirror's explicit "subpoena surface."

**2. Sealed sender, for devices.** Signal's [sealed sender](https://signal.org/blog/sealed-sender/) lets the server deliver a message without learning who sent it. The Mirror analog: when a device pushes a delta, the envelope proves "an authorized member of this family" without identifying *which device* — so the Mirror can't reconstruct which rooms of the house are active, or which family member's device syncs when. Authentication without identification.

**3. The Private Group System, for the family roster.** Signal's [private group system](https://signal.org/blog/signal-private-group-system/) (the [zkgroup anonymous-credential construction](https://eprint.iacr.org/2019/1416.pdf)) keeps group membership, names, and avatars stored *on* the server but encrypted, with members proving membership via anonymous credentials — the server hosts the group while learning nothing about it. The Mirror does the same for the family: the roster of enrolled devices (Layer 5's group state) can live on the Mirror for coordination and recovery, sealed, with devices presenting credentials that prove membership without revealing the family's shape. The vendor hosts thousands of families and can enumerate none of them.

**4. Attested enclaves, where the server must compute.** For the rare functions where the server has to *do* something rather than store something, Signal runs the code inside attested TEEs that clients verify before talking — private contact discovery, and [Secure Value Recovery](https://signal.org/blog/secure-value-recovery/), which enforces guess limits on a recovery PIN inside an enclave so that even Signal can't brute-force it. The Mirror can borrow SVR's shape for the recovery ceremony in Layer 5: a PIN-guarded, enclave-enforced, guess-limited recovery secret gives a family a lifeline that is still not vendor escrow. This is Layer 8's attestation machinery pointed in the opposite direction — the fleet attesting to devices becomes the server attesting to the family.

**Honesty clause.** Signal's history also teaches what zero-knowledge does *not* cover: traffic metadata. Padding and batching shrink what the Mirror observes, but timing and volume patterns are the residual leak, and the threat model should say so out loud rather than promise magic.

The protocol doesn't care which transport carried a given delta — gossip and Mirror are interchangeable carriers of the same sealed log. And a new device, once enrolled through Layer 5's ceremony, rebuilds its entire replica from the Mirror without the server learning what it restored.

## Trust boundaries, in one breath

With the model plane gone, there are exactly two cliffs where data changes trust domains, and both are cryptographic. **Process → disk** (encryption at rest, Layers 3/4/5). **Device → network** (E2EE at Layer 11, keys from Layer 5 — gossip peers and the Mirror both sit below this line and are untrusted). There is no policy-governed boundary anywhere in the system: no cleartext ever leaves a device, so there is nothing for a policy to leak. The control plane crosses no data boundary at all — it can update a device, but the worst it can do is brick one; it cannot read one.

---

## A note on build order

Top-down is the right way to *present* the stack; it is not the order to *build* it. The load-bearing spine is Layers 5 → 4 → 10 → 11: the crypto core, storage, replication, and transport — in effect, a boring, correct, multi-device encrypted sync engine with no AI in it at all, testable on commodity hardware long before custom devices exist. Pii (Layer 2) ships its first version with the smallest viable local model on devkit silicon — the GSD-style spec architecture is exactly what lets a modest model be useful early — and absorbs better weights over the Layer 6 channel as Layer 9 hardware firms up. The TEE (Layer 8) can begin life as a software keystore behind the Layer 5 interface and harden without breaking anything above it. FOTA (Layer 6) must exist before the first shipped unit — but not before the first prototype.
